# Sprint 2.5-B4.5-B2: local PostgreSQL catalog import adapter

## Scope and isolation

Starting branch `main`, HEAD `8b1e50a0ed199d4a174ae4981b3c942b2b5c2a3c`, clean worktree. This stage adds `src/lib/catalog-import/postgres.ts`, a server-side SQL adapter restricted at runtime to the **local test database** `catalog_import_test` on `127.0.0.1:55439`, owned by `catalog_test_owner`, with the previously verified Postgres.app data directory. Its only connection string is injected from the local test environment. It rejects passwords, query-string overrides, other hosts, ports, users, and database names. Each acquired connection checks the actual database, session user, socket address, port, listener, **pinned physical data directory and PostgreSQL system identifier**, and absence of `rfq_private` before any catalog SQL. The directory and system identifier are pinned in this local-only module; caller input cannot choose the trusted target. A private in-process mark prevents a caller from constructing `PostgresCatalogSnapshotReader` on an unchecked connection.

The B2 catalog migration was applied unchanged to this **second dedicated database** after local preflight. The B4.5-B1 `catalog_schema_test` database and RFQ test instance were not modified. All fixtures are synthetic. The local cluster uses loopback-only `trust` authentication for testing; this is not deployable authentication. There is no import API route, production Supabase client, service credential, or production write path.

## SQL reader and numeric mapping

`PostgresCatalogSnapshotReader` selects explicit columns from all six `catalog_private` business tables, including draft and retired rows. It maps PostgreSQL `NULL` to `null`, `TIMESTAMPTZ` to ISO text through the existing B4.5-A mapper, JSONB to the decoded object/array, and `numeric(14,4)` reference price to decimal text. It converts **only** `moq_quantity`, `order_multiple`, and `package_quantity` from PostgreSQL `int8` text (or bigint/number) to a number after a decimal-integer check and `Number.isSafeInteger` range check. Overflow and fractions fail explicitly; the adapter does not change the global `pg` type parser. `captureTrustedCatalogSnapshot` then validates identities, relationships, publication rules, freezes the snapshot, and computes the B4.4-A digest. The returned UUIDs are the real database identities.

## Transaction lifecycle and lock policy

`PostgresCatalogImportTransaction.execute` requires the B4.5-A in-process verified actor mark, a bounded request envelope, and the server-produced B4.2/B4.3 normalized batch. It rejects preview identities in input. It copies the batch before awaiting a connection. The SQL sequence on one connection is:

1. Physical connection preflight; `BEGIN ISOLATION LEVEL READ COMMITTED`; `SET LOCAL ROLE catalog_import`.
2. Bounded `lock_timeout`, `statement_timeout`, `idle_in_transaction_session_timeout`, and PostgreSQL 17 `transaction_timeout` for an overall transaction deadline.
3. One transaction-level advisory lock (`725604510131`), then `SHARE ROW EXCLUSIVE` locks in fixed order: categories, products, variants, category links, images, translations.
4. Look up the `(actor_id, idempotency_key)` receipt. If a matching fingerprint exists, return its stored result after commit; a different fingerprint returns `IDEMPOTENCY_CONFLICT`.
5. Reread all six tables, compare the expected B4.4-A snapshot version, rerun B4.4-B merge and its B3 final-state validation. Any issue aborts the whole batch.
6. Generate new UUIDs with the server's cryptographic UUID allocator; preserve existing UUIDs. Maintain a private preview-to-real map. Write products initially as draft, then variants, translations, category links, images, and finally product statuses. No category definition is modified; omitted child records are not deleted.
7. Reread and validate the complete final snapshot; insert the receipt; commit. The returned result is emitted only after successful commit.

The broad table locks deliberately serialize catalog changes during an import and protect the six-table snapshot from ordinary concurrent writes, including writers that do not take the advisory lock during this transaction. Every future catalog writer must adopt the same advisory key and lock order for its own correctness; a writer bypassing the protocol outside import transactions remains a risk. PostgreSQL unique indexes, foreign keys, RLS, row guards, and deferred publication triggers remain the final database checks. SQLSTATE lock/deadlock/timeout errors map to `TRANSACTION_TIMEOUT`; integrity conflicts map to `BATCH_INVALID`. SQL details and connection values are not returned in application errors. Failed transactions issue `ROLLBACK`, which releases locks and removes both business writes and the receipt. If rollback fails or PostgreSQL terminates the connection, the connection is discarded rather than returned for reuse.

## Local idempotency SQL design and impact assessment

The B2 six-table schema has no durable idempotency table. D2-A updated `scripts/catalog-import-local-receipts.sql` as a **test-only, unexecuted** fixture for `catalog_private.catalog_import_receipts`, aligned with the D1 draft. It uses `(actor_id,idempotency_key)` as primary key, a 64-hex fingerprint, a bounded allowlisted JSONB result, 30-day `retry_until`, 90-day `result_purge_after`, and a permanent `expired` tombstone. RLS restricts access to import/admin and narrow maintenance operations; anonymous and `rfq_api` receive no access. The old initialized local database still uses the prior table and cannot run the renamed adapter tests. A fresh, separately verified D2-B test database is required. Under the intended contract, receipt and six-table mutations commit atomically, the advisory lock serializes attempts, changed requests conflict, and expired keys cannot be reused. A lost response requires the same actor/key/request; `COMMIT_UNKNOWN` must not be retried with a new key. No production migration or route exists.

**Retention policy for this stage:** the isolated test script clears all receipts after each run, but only after re-verifying the physical database identity. The adapter never deletes receipts. No production retention or cleanup job exists. A future production deployment is blocked until the formal migration specifies a retention horizon and what happens to retries after expiry; deleting a receipt without an anti-replay rule could permit a duplicate import.

**Impact of a future formal migration:** one seventh private table, RLS policies and narrow grants would be required. The formal migration must be reviewed separately for role provisioning, result retention, audit access, cleanup policy, and deployment rollback. This stage does **not** add or modify a production migration or B2 Schema. The local SQL file has a database identity guard and was applied only after the exact local database and data directory were printed and checked.

## Validation results and known limits

The dedicated integration script resets only `catalog_import_test` synthetic rows after a physical-identity preflight repeated before **each** cleanup. It tests mismatched database/cluster rejection, draft and published creation, product/SKU updates, new SKU/translation/category/image associations, UUID mapping, B3 publication rejection, no-change imports, idempotent replay and key conflict, response-loss replay, two-connection concurrency, stale snapshots after category/translation changes, SQL SKU uniqueness, parameterized handling of SQL-like translation text, RLS denial, advisory-lock timeout, statement timeout, forced rollback-transport failure, and rollback at product, SKU, translation, category-link, image, and receipt writes. Test-only failure triggers are removed; business rows and receipts are truncated at completion. No RFQ table exists in this database.

Local integration: **18 tests passed**, including PostgreSQL 17's overall transaction deadline terminating a slow connection without partial writes. The B4.5-B1 post-migration script passed **28 checks** against its separate `catalog_schema_test` database. Remaining regression commands and worktree checks are recorded in the handoff report.

The adapter is intentionally bound to the isolated local test instance and cannot be used as a production connection implementation. Production readiness requires a separately reviewed idempotency migration, authenticated server-only database connection, an import API authorization design, audit logging, retention policy, and verification that all catalog write paths use the lock protocol. Category definitions remain outside the CSV import contract. Physical deletion remains prohibited by B2 rules for products and SKUs; relation removal is not implemented in this stage.
