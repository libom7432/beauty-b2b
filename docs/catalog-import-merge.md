# Sprint 2.5-B4.4-B catalog Patch merge

`mergeCatalogImport(parsed, snapshot, locate?)` is a pure, offline final-state projection. `parsed` is the B4.2 five-file result (also produced by B4.3 Excel conversion); `snapshot` must be the branded B4.4-A trusted snapshot. This module does not query a database, upload images, or issue SQL. It resolves identities through B4.4-A, merges all touched products with their **complete** existing SKU, translation, category and image rows, then invokes B3 `validateCatalogProduct` on each complete final product.

## Patch and identity rules

For update rows, `missing` and `blank` leave the current value intact. `clear` uses only the B4.1/B4.2 field allowlist and typed clearing value; `value` replaces the entire field, including JSON objects and arrays. For create rows, B4.2 supplies SQL defaults for absent optional columns. Neither absence of a child row nor a blank cell deletes a record. The five-file contract offers create/update only; category-link removal and other deletes require a separate future admin workflow. Product codes, SKU codes, UUIDs, ownership, and database-managed timestamps cannot be patched. Published Slug protection and retired reactivation policy remain in B4.4-A. A trusted category UUID is required; there is no implicit category creation.

All new product, SKU and image identifiers in the returned diagnostic final state use the deterministic, **non-UUID** `preview:<entity>:<sha256>` namespace. A discriminated `identity` field marks each product as `database` or `preview`; `PreviewCatalogId` distinguishes preview IDs in TypeScript. They are not database identities and cannot be supplied to PostgreSQL UUID columns. `assertNoPreviewCatalogIds` is an additional runtime guard for future adapters, not a persistence authorization check. B3 receives a separate internal validation view with deterministic temporary UUIDs so it can check same-product image/SKU links; those UUIDs are never returned. B4.5 must allocate or request real database IDs and reconstruct all relationships. B4.7 must reread and lock current state, rebuild the merge, and revalidate within the write transaction. The diagnostic result is not a database write DTO, even for existing-only updates.

PostgreSQL `numeric(14,4)` reference prices stay as decimal strings in final state; a numeric view is supplied only to B3 because its current validator accepts numbers. For a CSV price update, the exact typed cell's original decimal spelling is retained in the final state. This is an adapter boundary between B2 and B3, not a change to either contract.

## Result and batch failure

The result includes `snapshot_digest`, diagnostic `products` with original business identity and complete final state, field-level `changes` with file/row and optional Excel Sheet/column source, structured `issues`, and an `outcome` of `changed`, `unchanged`, or `invalid`. A change records its create/update operation, field, old/new value and cell state. Semantic equality of JSON objects is independent of object key order. B3 issues retain their stable error codes and are mapped back to the relevant source row where possible. If any parser, resolver, merge or B3 error exists, `valid` and `can_apply` are false for the **entire batch**. Diagnostic states and changes may still be returned for review; they are not an executable import plan. A true `can_apply` means only that the current offline snapshot and input passed this stage's merge and validation. It does **not** establish freshness, write permission, SQL readiness, or permission to skip B4.5/B4.7 transaction checks. An `unchanged` result has no field-level changes and needs no write.

The batch checks final Slug and image storage-key uniqueness across touched and untouched products. B4.2 and B4.4-A report duplicate product codes, duplicate/global SKU keys, invalid category/image references, and cross-product ownership. B3 checks final SKU attribute combinations, MOQ, price/currency, bilingual publication content, active primary category, and active primary image.

Example: updating `DEMO-A` with `oem=true` while leaving `attributes` blank produces a complete final `DEMO-A` with its existing attributes, SKU, translations, category and images, plus one sourced `oem: false → true` change. Clearing a published English name produces an `INCOMPLETE_TRANSLATION` error and makes the entire batch ineligible.

Run `npm run test:catalog-merge`. Tests use synthetic offline snapshots only. The B4.1 review draft left retired reactivation open; the later confirmed B4.4-A policy forbids it for CSV/Excel. B2 and B3 remain unchanged.
