# Sprint 2.5-B4.4-C offline Dry Run report

`createCatalogDryRunReport(input, snapshot, importSource, locate?)` accepts a B4.2 normalized five-file result or the **complete** B4.3 Excel conversion result, a branded B4.4-A trusted snapshot, and `csv` or `excel` as the source kind. Pass the complete Excel result so workbook mapping, formula, and conversion errors remain in the report and block review. It invokes B4.4-B merge and B3 final-state validation through that module. It opens no database connection, uploads nothing, and returns no SQL or executable write plan.

The report contains `report_id`, `import_source`, the complete `{contract, template_version, digest}` `snapshot_version`, `report_status`, `can_proceed_to_review`, product and issue counts, product-level results, safe field differences, errors and warnings. Product statuses map B4.4-B outcomes and individual errors to `created`, `updated`, `unchanged`, or `invalid`. A no-op update has `action: none` and no field differences. Product counts are computed from distinct final product results, not from upload-provided aggregate fields or SKU counts. Error counts include file-level errors without inventing a product identity; a file-level error can make the report invalid while `invalid_count` remains zero. Any error marks the whole report `invalid` and blocks review; an all-unchanged report is `no_changes` and has no update action.

Each product result includes SKU, translation, category and image create/update counts, its field differences, issues and actual source locations. Locations retain available CSV file/row/product/SKU and optional Excel Sheet/column information. Missing coordinates are omitted. The report never embeds complete product rows. Differences from create defaults with missing or blank cells are omitted to keep the report concise. Values from JSONB, translations, image URLs/keys and other potentially sensitive fields are redacted; safe scalar business fields remain visible. Error messages are generic by stable error code, and JSON attribute key paths are masked. Internal supplier data and database credentials are not part of this contract.

`report_id` is SHA-256 over a canonical projection of the normalized input and resulting safe report. JSON object keys are sorted, including nested attributes; the exact decimal spelling of an entered reference price is retained because B4.4-B preserves it in the final state. The same normalized business input and snapshot produce the same ID and report without a clock or random number. `report_id` identifies this offline diagnostic report; it is not a write token or concurrency lock.

`compareCatalogSnapshotVersion(expected, currentTrustedSnapshot)` returns `current`, `stale`, or `invalid`. The expected version must have the exact B4.4-A contract, nonempty template version and 64-character SHA-256 digest. A changed valid digest or template version is `stale`; malformed/unsupported versions or an untrusted current snapshot are `invalid`. A stale report must be rebuilt before review or later execution. `current` means only that the offline digests match and grants no write permission. This is **only an offline comparison**. B4.7 still needs a server-controlled database reread, locks, a new merge and validation inside the write transaction, and database constraints at commit.

Example: a batch updating `DEMO-A.oem` from `false` to `true` and creating a draft `DEMO-C` reports `total_products: 2`, `updated_count: 1`, `created_count: 1`, with one sourced, visible `oem` difference. Clearing a required published translation instead reports `invalid`, records the error, and sets `can_proceed_to_review: false`.

Run `npm run test:catalog-dry-run`; tests use synthetic offline snapshots only. Mock catalog and RFQ paths are unchanged.
