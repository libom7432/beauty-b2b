# B4-A Catalog PostgreSQL read adapter: local-only gate

Status: **adapter implemented and offline verified; the unmodified Catalog foundation migration and 13/13 integration tests passed against a dedicated local PostgreSQL 17.11 cluster. No real Supabase connection or cloud migration was made.** The local SQL tests do not authorize production connection. F8 implemented the approved read-only UUID Admin detail route and compact HMAC-SHA256 cursor V2; the adapter is still not connected to the production server entry point.

## Schema gap report (formed before adapter implementation)

`supabase/migrations/20261013120000_create_catalog_foundation.sql` defines six `catalog_private` tables (`products`, `product_variants`, `categories`, `product_categories`, `product_images`, `product_translations`) and six filtered `catalog_public` views with matching names. The existing B1 private and public row DTOs match their selected columns. `numeric(14,4)` and `bigint` must remain text at the query boundary. Timestamps need microsecond-preserving UTC text for signed keyset boundaries; the default `pg` Date parser would discard microseconds. No tier-price, collection or stock tables exist, so the adapter must not synthesize them.

**Blocking database gap:** the foundation migration grants draft-capable reads only to write-capable `catalog_admin` and `catalog_import`. `catalog_public_reader` is published-only under RLS. There is no dedicated login role with SELECT-only private access to drafts and retired products. B4-A does not alter the migration or provision a real role. A separately approved role/RLS migration and effective-privilege audit are required before any deployment. The private tables have RLS enabled but not FORCE RLS; the runtime role must be a non-owner without `BYPASSRLS`, inherited writer membership, or RFQ/import rights. Public views remain filtered and must never be replaced by private-table projections.

**Product Code compatibility:** SQL permits any trimmed nonempty text and has a case-sensitive unique constraint. Sprint 2.5 import also rejects C0 control characters and CSV fields beyond 32,768 UTF-16 code units. F6 expanded legacy Admin detail validation to this existing import domain without changing the migration or import rules. Synthetic `CN-甲` opens by Product Code and works as a `product_code_asc` boundary in real PostgreSQL. Slash, whitespace, Unicode and reserved URL characters use a canonical base64url single-segment legacy detail route; conventional ASCII legacy links retain their old URL. F8 changed new list links to bounded UUID detail URLs and issues only compact, signed V2 Admin cursors. V2 carries a UUID boundary reference, not Product Code, and the cursor and Admin URL parser share a 1,024-character maximum. The SQL `text` type itself has no 32,768-character maximum and accepts some control characters that import rejects. Such directly inserted out-of-contract rows still need an explicit policy before live cutover. Very long legacy Product Code URLs can exceed browser or proxy limits; this needs deployment-limit testing. Existing indexes cover uniqueness and some public/status queries, but not every Admin sort or substring name search. No performance plan has been measured.

## Adapter boundary

`src/lib/catalog-read/postgres-core.ts` implements `CatalogReadSource` through an injected, read-only query/snapshot interface and static, parameterized SQL. It returns the established B1 bundles; the Repository still performs `catalog.read`, signed cursor verification, mapping and sanitized errors. `src/lib/catalog-read/postgres-local.ts` is the `server-only` Node `pg` entry point. Its pure, offline-tested configuration guard in `postgres-local-config.ts` accepts only the canonical TCP target `127.0.0.1:55432/beauty_b2b_catalog_test` as `catalog_read_local` with an explicit test credential and `NODE_ENV=test`; it rejects URL overrides, other local databases and production. It is **not wired into** `src/lib/catalog-read/server.ts` or any route. Missing local configuration leaves the live site `NOT_CONFIGURED`. URL parameters cannot choose this source.

The pure SQL core has no credential or connection and is deliberately importable by Node offline tests. Only `postgres-local.ts` can construct the real pool. Its read operation uses `BEGIN ... REPEATABLE READ READ ONLY`, fixed query/connection timeouts, and sanitized connection errors. Missing configuration or an unavailable local connection is `NOT_CONFIGURED`; a failure after connection is `SOURCE_UNAVAILABLE`. The local smoke script additionally requires `RUN_LOCAL_CATALOG_READ_TESTS=1`; an invalid or non-loopback configured URL fails before connecting. With the switch absent, the test reports one **skipped** test, not success. This entry is not a production configuration switch.

The local test login design is `catalog_read_local LOGIN NOINHERIT NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE`, not a table owner. Grant database CONNECT, USAGE on `catalog_private` and `catalog_public`, SELECT on the six named private tables and six views, and matching SELECT-only RLS policies on the private tables. Revoke direct writes, TRUNCATE, sequence privileges, RFQ schema access and import function EXECUTE; audit inherited and PUBLIC privileges. No SECURITY DEFINER is needed. This is a **design**, not a migration. Admin Auth and the database login are distinct; `catalog.read` is checked before source access.

## Isolated local PostgreSQL integration

The dedicated Postgres.app 17.11 cluster is under `~/Library/Application Support/BeautyB2B/pg17-b4-test/`, with separate `data`, `socket`, and `logs` directories. It listens only on `127.0.0.1:55432` and uses local peer and TCP SCRAM-SHA-256 authentication. The existing Postgres.app `var-17` cluster was untouched. Database `beauty_b2b_catalog_test` contains the **unmodified** `20261013120000_create_catalog_foundation.sql` foundation migration, a local-only `anon NOLOGIN` prerequisite, synthetic fixtures, and local-only test policies. No other project database or Supabase service was used. The cluster has no startup service and is normally stopped after the test run; retained data permits repeat testing.

`scripts/setup-catalog-read-postgres-local.mjs` is a one-time initializer guarded by the exact local cluster path, port, database, and empty catalog. It creates `catalog_read_local` and a separate no-policy login, six `FOR SELECT` RLS policies, a synthetic RFQ sentinel, a synthetic import function, and nine synthetic products. Passwords are generated at runtime and stored with owner-only permissions **outside this repository** under the dedicated cluster directory. The script must not be rerun against populated data. Test roles are neither table owners nor superusers, have no `BYPASSRLS`, no inherited writer role, and no `CREATE` on the database or Catalog schemas.

Start and stop **only** this dedicated cluster with the Postgres.app 17 binary and an explicit `-D` path; never rely on default PG targets. After it is running, `node scripts/run-catalog-read-postgres-local.mjs` verifies the database's actual data directory, port, and listener via the local peer socket, loads the dedicated test credentials from outside Git, then runs `scripts/test-catalog-read-postgres-local.mjs` over real PostgreSQL. The launcher refuses production `NODE_ENV`. The test suite also verifies its login, database, port, and listener, and rejects non-loopback configured URLs. Do not run the one-time setup script again merely to rerun tests.

The dedicated local PostgreSQL integration suite has **13/13 passing tests**. They cover the six private tables and six public views, selected constraints/indexes/RLS, role attributes and effective privileges, actual write/RFQ/import denial, RLS default denial for the separate login, draft/published/retired reads, UUID and Product Code detail mapping, English/Chinese/literal-LIKE search, filters, all four sorts, multi-page Next/Previous with equal timestamps, empty/single pages, malformed cursor and authorization, public view filtering, sanitized connection failure, Unicode Product Code keyset compatibility, and a 32,768-character Chinese boundary. These are local results; real Supabase credentials, grants, policy deployment, concurrent updates, and production performance remain **unverified**.

## Query and correctness notes

Candidate IDs are filtered, keyset-paged and bounded in PostgreSQL before hydration. Admin ordering is `updated_at DESC/ASC` or `product_code COLLATE "C" DESC/ASC`, then `id ASC`. Previous uses inverse SQL order including `id DESC`, fetches one extra row, and reverses the returned page. Search is a trimmed lowercase JavaScript term sent as a bound `ILIKE` pattern with `%`, `_` and backslash escaped; Chinese matching is literal substring under database collation. Public candidates and hydration read only the six `catalog_public` views. Category ancestors are fetched through a depth-limited recursive query. Each hydration relation has a 5,001-row SQL cap; exceeding 5,000 fails safely instead of silently truncating. Each list/detail read runs in a repeatable-read, read-only transaction when using the local `pg` entry point. No cross-request snapshot is promised.

F8 V2 uses HMAC-SHA256 with a server-only key, constant-time comparison, Admin scope, query fingerprint, sort, direction and a UUID boundary witness. The source resolves the signed reference under the current filter before Keyset paging and rejects a missing or changed boundary. Old V1 signed links are rejected immediately; reopen the list from its first page. Old Product Code detail routes remain authorized but are limited by browser and proxy URL lengths for unusually long codes. A read-only transaction gives consistency only **within one request**; concurrent changes across requests can still alter pagination.

## Remaining gates

Local PostgreSQL syntax, RLS, reader privileges, search, and static-data pagination have been verified. The local adapter remains **unwired** to the live Next.js server. Browser response isolation was checked through existing offline/isolated browser tests, not through a real database-backed browser route. Validate deployment URL limits for unusually long legal codes before live catalog cutover. A production-ready read identity, Supabase-supported connection method, real grants/policies, credential rotation, performance, concurrent-update pagination, and deployment-specific behavior are **not verified**. Do not connect any real Supabase project or enable this adapter in production from this B4-A work. Existing RFQ and import contracts and production permissions are untouched.
