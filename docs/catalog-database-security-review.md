## Formal receipt migration proposal

The proposed table is `catalog_private.catalog_import_receipts`. The B4.5-B2 **local-only** table and adapter currently use `catalog_private.product_import_receipts`; this is a deliberate naming difference, **not** a compatible drop-in migration. D2 must change the adapter's fixed SQL table name, result handling, expiry checks, and local tests as one reviewed change. Do not deploy this draft under the old adapter.

| Field | Type / rule | Purpose |
| --- | --- | --- |
| `actor_id`, `idempotency_key` | nonempty bounded opaque text; composite primary key | Server-verified actor and permanent non-reusable key. Never taken from an unverified client role claim. |
| `request_fingerprint` | 64 lowercase hex SHA-256 | Canonical request fingerprint from the existing B4.5-A function, including batch ID, source, expected snapshot, parsed rows and issues. It is comparison data, not authorization. |
| `status` | `committed` or `expired` | Committed receipt or permanent tombstone. No `in_progress` row is needed with the global transaction lock and atomic commit. |
| `result` | bounded JSONB object while committed; `NULL` when expired | Sanitized `DatabaseWriteResult` only: status, batch ID, snapshot version, product count, internal identity map and replay marker. No CSV/Excel body, translations, image URLs, customer data, credentials or SQL errors. D2 must serialize an explicit allowlist and keep the identity map server-side. |
| `created_at`, `completed_at` | `timestamptz` | Receipt creation and successful transaction completion. |
| `retry_until` | `completed_at + 30 days` | End of the promised same-key replay window. |
| `result_purge_after` | `completed_at + 90 days` | Earliest time the full result can be removed. |
| `expired_at` | nullable `timestamptz` | Records when the result was purged and the tombstone began. |

The composite primary key is the identity/uniqueness constraint. A partial index on `(result_purge_after, actor_id, idempotency_key)` for committed rows supports bounded maintenance scans. No raw request body or content-derived text is indexed. The draft enforces result shape, a size cap, timestamp relationships, and `committed`/`expired` consistency; D2 still needs strict server-side JSON allowlisting because a database `jsonb` check cannot prove that a nested string is nonsensitive.

**Three distinct lifetimes:** an accepted `(actor_id, key)` is **never valid for reuse**; the guaranteed retry window is 30 days; full result retention is 90 days. During days 31–90, the row remains but an original retry returns `IDEMPOTENCY_KEY_EXPIRED`, not a replay or a new import. After day 90, a maintenance role changes the row to a permanent tombstone and clears `result`; the primary key and fingerprint remain. A retry then returns the same expiry error. A different fingerprint for the same key always returns `IDEMPOTENCY_CONFLICT`. D2 must check the existing row **before** snapshot-version validation, under the global lock, using database time. Expired keys never fall through to the create path. Tombstones are not physically deleted by routine cleanup. Indefinite actor/key/fingerprint metadata retention requires privacy and capacity approval before production migration; if policy forbids it, D2 needs a different durable anti-replay registry, not silent deletion.

The receipt is inserted in the **same transaction** as catalog writes. Concurrent duplicate requests serialize on advisory/table locks and the primary key remains the final arbiter. A same-key, same-fingerprint retry within the window returns the original result even if a later import changed the catalog. A changed fingerprint conflicts. An uncertain `COMMIT` must be resolved with the original actor, key and request; no new key is allowed. A transaction that never committed has no receipt and can be retried after a fresh version check. Migration rollback is an application rollback: disable the import entry point, retain the table and old receipts, and deploy compatible readers. Do **not** drop a populated receipt table, as that would reopen accepted keys. A physical `DROP TABLE` is permissible only in an independently approved empty/prelaunch environment after proving no accepted requests exist.

## Permission matrix and RLS

`catalog_public` is a **schema**, not a database role. `catalog_public_reader` is the NOLOGIN view owner. The following is the effective B2 design for the six catalog tables plus the proposed receipt; it is not a new grant applied in D1.

| Principal | Six private catalog tables | Public views | Proposed receipt | RFQ private tables | Import execution |
| --- | --- | --- | --- | --- | --- |
| `anon` | No schema usage, SELECT or DML | SELECT published-only explicit columns | None | None | No |
| `catalog_public_reader` | SELECT subject to published-only RLS; no DML | Owns views, NOLOGIN | None | None | No |
| `catalog_admin` | SELECT/INSERT/UPDATE/DELETE grants; B2 guards block physical product/SKU/category deletion | Schema usage | SELECT only in draft | None from these migrations | Only through an authenticated service that invokes the import path under `catalog_import` |
| `catalog_import` | SELECT/INSERT/UPDATE; no DELETE. Existing B2 grant includes categories, although the current adapter issues no category DML | Schema usage | SELECT/INSERT only in draft | None | Trusted service only, after server authentication and `SET LOCAL ROLE` |
| `catalog_receipt_maintenance` (proposed) | None | None | Narrow SELECT and UPDATE of expiry fields only; no DELETE | None | No |
| `rfq_api` | None | None | None | Narrow INSERT of RFQ request/item/job fields and SELECT of request metadata only; no UPDATE/DELETE | No |

B2 enables RLS on all six base tables. `anon` has no private schema usage and reads security-barrier views owned by `catalog_public_reader`, whose RLS policies filter published rows. The draft enables and forces RLS on receipts; import gets SELECT/INSERT policies, admin gets SELECT, maintenance gets due-row SELECT/UPDATE. Grants **and** RLS must both allow an operation. The draft grants no receipt DELETE, public access, or RFQ access and defines no `SECURITY DEFINER` function. B2 catalog trigger functions and RFQ timestamp functions use a pinned `pg_catalog` search path and default invoker rights. D2 must audit actual role attributes, memberships, object ownership, default privileges, `PUBLIC` privileges, schema `CREATE`, `BYPASSRLS`, and effective `SET ROLE` on the deployment target. A superuser, table owner without FORCE RLS on B2 tables, or Supabase `service_role` can bypass ordinary policy; **do not use such an identity for the production import connection**. `REVOKE` from `service_role` alone cannot constrain a bypass-capable role.

The existing B2 migration grants no LOGIN or database CONNECT to `catalog_admin` or `catalog_import`. A future dedicated server login must be provisioned out of band, with no owner/superuser/BYPASSRLS rights and only explicit `SET ROLE catalog_import` capability; it must use schema-qualified SQL and a transaction-local `search_path=pg_catalog`. No browser credential or self-asserted `actor_id` may select that role. The current local test owner is privileged and uses loopback `trust` authentication: its role-switch tests verify grants/RLS but do **not** prove production network authentication. The isolated catalog database contains no RFQ tables, so RFQ-side effective permissions require a separate deployment-target audit; D1 changes none of them.

## Uniform catalog write-lock protocol

For bulk import, future admin create/edit, SKU and price update, category-tree adjustment, publication/retirement, and image-link update, require one controlled transaction path:

1. Authenticate the actor on the server, authorize the operation, validate inputs, and reject preview UUIDs in persistence fields. Use a dedicated non-bypass connection and `SET LOCAL ROLE` for the operation.
2. `BEGIN ISOLATION LEVEL READ COMMITTED`. Set bounded `lock_timeout`, `statement_timeout`, `idle_in_transaction_session_timeout`, and (on PostgreSQL 17+) `transaction_timeout`. The current local adapter defaults to 2 s, 10 s and 30 s; D2 must set environment-specific limits and test PostgreSQL version compatibility.
3. Acquire `pg_advisory_xact_lock(725604510131)` first. Lock six tables in this fixed order with `SHARE ROW EXCLUSIVE`: `categories`, `products`, `product_variants`, `product_categories`, `product_images`, `product_translations`. Where additional row locks are needed, acquire category, product, SKU and child rows in a documented UUID order after table locks. No RFQ table participates.
4. Reread the trusted six-table state **after** locks, compare the expected B4.4-A snapshot version, merge the final state and rerun B3 validation. For non-import edits, use the same complete-state validation and version check. The digest detects stale state; it is not a lock.
5. Write in foreign-key order, rely on global uniqueness, FK, immutable-identity guards and deferred publication triggers, then commit. A losing writer receives `SNAPSHOT_STALE`, `IDEMPOTENCY_CONFLICT`, an integrity conflict (`BATCH_INVALID`), or a bounded timeout/deadlock response after rollback. `COMMIT_UNKNOWN` requires same-key recovery, never blind retry with a new key.

The existing B4.5-B2 import path follows the global advisory/table-lock protocol and B4.5-B3 tests it with multiple connections. **No management backend exists yet**, so this review does not claim that future admin writers follow it. Any writer that bypasses the advisory protocol can race with another bypassing writer outside an import transaction. D2 must document a common server utility or DB-side enforcement strategy before adding another write path. Broad table locks trade throughput for correctness; changing them requires separate concurrency tests.

## Cross-process recovery verification

Against the previously verified local `catalog_import_test` cluster (`127.0.0.1:55439`, expected database/user/data directory/system identifier, no RFQ schema), a synthetic request was saved in ignored `work/`. Process A executed the existing adapter with a **simulated lost COMMIT acknowledgement**, observed `COMMIT_UNKNOWN`, and exited without reading the receipt. A separate Node process B rebuilt a verified actor, submitted the identical normalized request and original key, and received `replayed=true` and `status=committed`. The database contained exactly one product and one receipt. Cleanup rechecked the physical database identity, then removed the synthetic rows; final counts were zero. This verifies durable local receipt recovery across process boundaries for the **current local table**, not the unexecuted formal draft or a production service restart. B4.5-B2/B3 tests separately cover rollback, response loss and concurrent retries.

## Production isolation and D2 prerequisites

The present adapter is hard-pinned to the local Postgres.app cluster, checks actual server identity on every connection, rejects passwords/remote URLs, and has no public route. No production import API exists. A future endpoint must be **default disabled** (explicit deployment switch, otherwise 404/deny), server-only, authenticated and authorized, rate/size limited, CSRF-protected where browser sessions apply, and unavailable to anonymous or RFQ roles. Its credentials must come from a managed secret store at runtime, never browser bundles, repository files or logs. Logs should contain correlation IDs and stable error codes, not imported rows, translation text, image URLs, receipt JSON, customer details, SQL parameters or connection strings. Production migration requires separate human approval, a verified target identity, a reviewed migration plan and a post-deployment privilege audit. D1 made no production connection or migration.

Before B4.5-D2: approve permanent anti-replay tombstones and data-retention policy; review the draft's exact SQL and PostgreSQL-version compatibility; reconcile `catalog_import_receipts` with the adapter's local `product_import_receipts`; implement explicit result allowlisting and `IDEMPOTENCY_KEY_EXPIRED`; provision and audit service/maintenance role access without BYPASSRLS; test receipt expiry and rollback in a fresh isolated database; verify cross-process replay after applying the approved formal schema locally; audit effective catalog and RFQ grants on the eventual target without broadening RFQ rights; retain the production API disabled until its own security review.
