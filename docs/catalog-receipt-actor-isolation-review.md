# Sprint 2.5-B4.5-D2-B2-B4-A: receipt actor isolation design

## Scope and evidence

Design only. Starting branch `main`, HEAD `840027f8ce6ffb029f695a79d1e2213b32af772d`; the D2-A/B1/B2-B1 worktree changes are preserved. Reviewed the executed D1 receipt draft, D2-A contract, B4.5-B2/B3 transaction design, `postgres.ts`, `receipt.ts`, `transaction.ts`, and the D2-B2-B3 isolated-database result. This review neither changes the executed SQL draft nor applies privileges, migration, cleanup, or catalog writes. The local 55440 test cluster has the receipt table and zero business/receipt rows; its prior independent-login test confirmed the cross-actor read.

## Current permission and transaction boundary

| Principal | Receipt grant | Receipt RLS | Consequence |
| --- | --- | --- | --- |
| `catalog_import` | table `SELECT`, `INSERT`; no `UPDATE`/`DELETE` | `SELECT USING (true)`; `INSERT WITH CHECK (status='committed' AND result IS NOT NULL)` | Can read **every** actor's receipt and insert under any syntactically valid `actor_id`. |
| `catalog_admin` | table `SELECT` | `SELECT USING (true)` | Can read every actor's receipt; no default business need has been established. |
| `catalog_receipt_maintenance` | SELECT of four metadata columns; UPDATE of `status`, `result`, `expired_at` | Due-row SELECT and expiry-only UPDATE | May see due-row metadata and expire it; cannot directly read `result` or edit product tables. |
| `anon`, `catalog_public_reader`, ungranted roles | none | none | No direct receipt access. |

All catalog roles above are `NOLOGIN`, `NOINHERIT`, without `BYPASSRLS`, but a trusted server login can assume `catalog_import`. `NOLOGIN` prevents direct authentication as that role; it does **not** isolate actors sharing the role. B2's six catalog tables retain their separate grants and RLS. The D2-B2-B3 test used a real non-superuser login and confirmed `catalog_import` can read both actor A and actor B rows. The isolated database has no RFQ schema, so RFQ table-level privileges were not tested there.

The current adapter obtains a server-verified `ActorContext` through an in-process verifier. In one `READ COMMITTED` transaction it assumes `catalog_import`, takes advisory lock `725604510131`, locks six catalog tables in fixed order, then selects the receipt with `WHERE actor_id=$1 AND idempotency_key=$2`. A matching receipt is considered before snapshot-version comparison; `replayCatalogReceipt` checks fingerprint, status and the database-clock 30-day flag. On a new import, catalog writes and the allowlisted receipt insert commit atomically. `COMMIT_UNKNOWN` recovery resubmits the same actor, request and key, and requires access to the original receipt. Concurrent equal-key requests serialize on the advisory lock and are ultimately guarded by the `(actor_id, idempotency_key)` primary key. SQL parameters protect the normal query from injection, but the normal `WHERE` clause and the TypeScript actor brand do not constrain arbitrary SQL issued with the same database role.

## Options

| Question | A. Revoke SELECT; restricted accessor | B. Session actor context plus RLS | C. Per-actor DB principal plus restricted accessor |
| --- | --- | --- | --- |
| Actor source | Server passes `actor_id` to an accessor unless another binding is added. | Server sets a session value. | Auth service provisions a dedicated non-superuser DB login and immutable mapping to its verified actor; PostgreSQL supplies `session_user`. |
| Forgery boundary | A shared caller can pass another actor ID; key secrecy is not authorization. | A shared caller can call `set_config`/`SET LOCAL` for another actor. | One actor login cannot change `session_user` to another actor or assume another actor login. Central service holding all credentials remains fully trusted. |
| Grants/RLS | Remove direct SELECT; grant narrow `EXECUTE`. Accessor owner needs constrained receipt read rights. | Shared role keeps SELECT; RLS compares `actor_id` with mutable session value. | Remove direct SELECT from import/admin; bind INSERT RLS and accessor-owner SELECT RLS to a protected `session_user` mapping. |
| Function/search path | `SECURITY DEFINER` required; explicit columns, no dynamic SQL, pinned `pg_catalog` path and no PUBLIC execute. | No definer is necessary for a plain GUC, but the GUC is attacker controlled. A signed context requires a separately protected verifier. | Two small audited definer functions read the protected mapping and own receipt; fixed schema-qualified SQL, pinned `pg_catalog` path, no dynamic SQL or PUBLIC execute. |
| `SET ROLE`, injection | A shared role can invoke the accessor with another actor ID; injection can do the same. | A shared role can reset the context; connection-pool context leakage is another risk. | `SET ROLE catalog_import` leaves `session_user` unchanged; no actor login has membership in another actor, owner, reader-owner or maintenance role. Injection under one actor's credential can reach only that actor's receipt, though catalog DML remains a separate risk. |
| Replay/concurrency | Compatible if lookup precedes version check under the same advisory lock. | Technically compatible, but unsafe identity binding. | Compatible: lookup takes only the key, uses the same transaction/lock and DB clock, and replays the same result; a restarted process must reconnect as the **same actor DB principal**. |
| Complexity | Low to medium; **does not prove actor isolation** with a shared role. | Low for plain GUC but insecure; signed assertions add key management, expiry and replay controls. | High: principal lifecycle, credential vault, per-actor connection pools, mapping and revocation. Provides a database-enforced actor boundary under its assumptions. |

An A-only accessor or unsigned B must not be described as database-level actor isolation. A signed session assertion could be viable if an independent identity service signs actor, audience, request scope, nonce and short expiry, and PostgreSQL verifies it with a secret unavailable to the shared import role. That is a distinct, higher-complexity design and is not present today.

## Recommendation: C with the restricted read surface from A

Use a **separate database login for each authorized import actor**, provisioned by a trusted server identity service after authentication. The browser never receives the credential or direct database access. Store credentials in a managed secret store, not the repository, request body or logs. Each login is `NOINHERIT`, non-superuser and without `BYPASSRLS`; grant only the ability to `SET ROLE catalog_import`. It has no membership in another actor login, `catalog_admin`, receipt function owner, maintenance role, table owner, or privileged service roles. The role-to-actor mapping is unique in both directions, writable only by a separate provisioning identity; normal import sessions cannot create or modify it. A disabled/revoked actor mapping resolves to no actor. `session_user`, unlike a client GUC, remains the authenticated login after `SET LOCAL ROLE catalog_import`.

Apply a **separate incremental migration** after the executed receipt draft; do not edit or replay that draft. Its reviewed SQL must: (1) create the protected principal mapping and narrowly privileged function-owner roles; (2) revoke direct receipt `SELECT` from `catalog_import` and `catalog_admin`; (3) replace `SELECT USING (true)` with actor-bound policies for the accessor owner and bind import `INSERT WITH CHECK` to the mapped actor; (4) expose an accessor accepting an idempotency key, **not an actor ID**, returning only `request_fingerprint`, `status`, allowlisted `result` and the database-clock retry flag; (5) keep the maintenance policy separate. Unmapped sessions must see/insert nothing. The current broad admin SELECT should not survive by default; exceptional cross-actor support access needs a separate time-bounded, audited break-glass design.

The mapping lookup function is `SECURITY DEFINER`, `STABLE`, owned by a `NOLOGIN` role with only mapping-table SELECT. The receipt accessor is another audited `SECURITY DEFINER` function whose owner has only receipt SELECT and a receipt RLS policy scoped by the same `session_user` mapping. Both use fixed, schema-qualified SQL, `SET search_path = pg_catalog`, no dynamic SQL, no caller-supplied role/actor identifier, and explicit `REVOKE EXECUTE FROM PUBLIC`; only `catalog_import` may execute the receipt accessor. The mapping table itself is private, with no SELECT or DML for import/admin/anonymous roles. `FORCE RLS` stays enabled on receipts. Function ownership, default privileges, effective `SET ROLE`, temp-object shadowing and `BYPASSRLS` require independent review. Test any PostgreSQL owner/RLS behavior with real non-superuser logins; a superuser test proves nothing here.

The server compares its verified `ActorContext.actor_id` with the database-resolved actor before import. The database binding, not that comparison alone, enforces receipt isolation. A production adapter must replace the current owner-pinned local connection with a separately reviewed per-actor connection broker; no public import endpoint exists today. It must call the accessor after acquiring the existing global lock and before snapshot validation, and keep direct receipt INSERT in the same transaction as catalog writes. RLS rejects an inserted `actor_id` different from the mapped session actor. The primary key, request fingerprint, 30-day database-clock check, 90-day retention fields and permanent tombstone remain unchanged. Recovery after `COMMIT_UNKNOWN` reconnects as the original principal with the original key and request. A same-key request from another actor has a different composite key and cannot read or replay the first actor's row.

This is a **database-level boundary between distinct actor credentials**, not a defense against compromise of the central credential broker, database owner, superuser, or a principal authorized to provision mappings. If operations cannot support per-actor DB authentication, strict actor isolation is **not achievable with the current shared `catalog_import` login alone**. A-only can reduce accidental disclosure but must remain a production blocker until a different cryptographically bound identity design is approved.

## 90-day maintenance boundary

Keep the dedicated `catalog_receipt_maintenance` `NOLOGIN` role, with a distinct server-only maintenance login that cannot assume `catalog_import`, `catalog_admin` or actor roles. No browser or ordinary import principal may invoke maintenance. A future reviewed maintenance entry point runs a bounded `READ COMMITTED` transaction: verify the target and caller, acquire advisory lock `725604510131` before row locks, choose due committed rows in stable `(result_purge_after, actor_id, idempotency_key)` order, then update only `status='expired'`, `result=NULL`, `expired_at=clock_timestamp()`. Use database time, bounded lock/statement/transaction timeouts and rollback on failure. Keep `(actor_id,idempotency_key)`, fingerprint and deadlines permanently; never grant DELETE or let an expired key enter the create path. Concurrent import/replay and maintenance must obey the same lock protocol. The existing due-row RLS and column grants are a useful base, but the worker, its authentication, lock order and true 90-day behavior remain unimplemented. Logs should contain correlation/job IDs, row counts and stable error codes, never keys, actor IDs, receipt JSON, credentials or SQL parameters.

## Isolated PostgreSQL verification plan

Before any SQL test, recheck the approved local host, port, database, session user, data directory, listener, system identifier, server version, table inventory and zero real-business-data condition. Apply only an approved incremental migration in that isolated cluster; never modify B2, RFQ, or the executed receipt draft. Create **two separately authenticated non-superuser actor logins** plus an unrelated role and a dedicated maintenance login. Assert neither actor login has `BYPASSRLS`, privileged memberships or `SET SESSION AUTHORIZATION` ability for another actor.

1. A and B can each recover their own committed receipt through the key-only accessor; B gets no row for A's key, even when the key is known.
2. Anonymous, unrelated and unmapped logins cannot call the accessor or read/insert receipts. Direct receipt `SELECT` by import/admin/ordinary actor logins is denied; only the narrowly privileged function owner has its reviewed read path.
3. A cannot insert a row labelled B, cannot change its own session mapping, cannot `SET ROLE` B/owner/maintenance, and cannot forge a GUC to affect receipt visibility. Direct SQL injection attempts under A's DB credential remain actor-scoped.
4. Two connections using A and the same key serialize to one write and one replay; a different fingerprint conflicts. A restarted process using A's credential resolves `COMMIT_UNKNOWN`; B cannot recover A's result.
5. Replay works through the exact 30-day boundary, rejects after it, and permanently rejects an expired tombstone. Different fingerprints conflict before expiry evaluation. No host-clock manipulation is used.
6. Maintenance sees only due metadata, cannot read `result` or modify products, cannot assume import/admin/actor roles, and cannot grant itself more rights. Its approved expiry transaction preserves actor/key/fingerprint and rolls back on failure; repeat execution is idempotent. Test race with import under the common advisory lock.
7. Audit effective GRANT, RLS, function owner, `SECURITY DEFINER`, pinned `search_path`, PUBLIC/default privileges, schema CREATE, role memberships and `BYPASSRLS` using actual independent logins. Log denied access minimally; never log receipt bodies or parameters.

## Incremental rollout and residual risk

Production migration and import API remain unapproved. Before D2-B2-B4 implementation, approve the per-actor credential/provisioning lifecycle, mapping ownership and revocation procedure, exact incremental SQL, definer-function review, admin support-access policy, maintenance identity, and isolated-test target. The adapter and incremental SQL must land together while the production import API stays disabled; a mismatch must fail closed. If rollout fails, disable import/replay access and retain the receipt table and tombstones; do not restore broad SELECT or drop a populated table. Run a separate production-target privilege audit only after its own approval.

Residual risks: central broker/vault compromise spans actors; per-actor pools and role count add capacity cost; in-flight sessions may survive role revocation until terminated; B2 product DML remains broad for `catalog_import`; catalog writers outside the global lock can still conflict; no automated 90-day purge or production auth has been validated. This review adds no database object and makes no claim of deployed isolation.
