Both `admin-ui.spec.ts` and `admin-products-read.spec.ts` use this helper. The test identity is a cookie recognized only by the temporary replacements. The repository's production Auth code has no fixture switch. A fresh 32-byte random test signing key is passed only to that child process; no real Supabase URL or database credential is needed. Fixture cleanup also runs if startup fails. The ordinary Playwright web server still exercises anonymous production-source routes with credentials blanked.

**Implemented / offline verified query path:** `/admin/products` URL parameters are parsed by `parseAdminProductsUrl`; `requireAdminPage("catalog.read")` runs before server repository construction; `listAdminProducts` checks `catalog.read` again, validates and verifies a signed Admin cursor, and only then calls a source. The offline source applies code/English/Chinese substring search, status and *primary* category filters, stable sorting, and bounded keyset paging before DTO mapping. `product-list-panel.tsx` renders the DTO, distinct disconnected/empty/no-match/source-error states, and signed Next/Previous links. URL parameters cannot choose the source or grant a role. The page does not read all products and filter them in a component.

**Unverified:** The temporary server cannot prove real Supabase Auth, Postgres RLS, network failures, pooler behavior, or concurrent-update snapshot stability. The production server entry currently uses `notConfiguredCatalogSource` and does not connect to a catalog database.

## Dedicated database read identity — design only

The foundation SQL at `supabase/migrations/20261013120000_create_catalog_foundation.sql` creates six `catalog_private` tables and six filtered `catalog_public` views. It grants `catalog_admin` writes, `catalog_import` import rights and `catalog_public_reader` published-only SELECT under RLS. None is suitable as the Admin read runtime. The private tables have RLS enabled, but not FORCE RLS; the proposed login must be a non-owner, non-superuser role without BYPASSRLS and without membership in owner, `catalog_admin`, `catalog_import`, RFQ, `service_role`, `authenticated`, or `anon`. Existing-role inheritance, database-level privileges and default PUBLIC privileges must be audited in the target environment.

Proposed separately reviewed migration: create one dedicated `LOGIN NOINHERIT` role such as `catalog_admin_reader_runtime` (name illustrative); grant only database CONNECT, `USAGE` on `catalog_private`, and SELECT on the six named private tables, narrowed to required columns after the adapter's select list is finalized. Add SELECT-only RLS policies for that exact role on products, variants, categories, product_categories, product_images and product_translations, permitting Admin rows regardless of publication state. Do not grant INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER, CREATE, schema ownership, public-view ownership, sequence access, RFQ schema/table access, or import receipt/function execution. Do not use SECURITY DEFINER. Do not grant broad role membership. Explicitly review and revoke unintended schema/table/function privileges from PUBLIC and this runtime role; PostgreSQL functions may have default PUBLIC EXECUTE. Preserve necessary grants for existing actors. Add owner-specific `ALTER DEFAULT PRIVILEGES` rules so future catalog tables/functions are not silently exposed, and audit effective privileges after creation. The exact migration syntax, policy interactions and bootstrap credentials require separate approval and isolated execution; **no role or policy is created here**.

Next.js must connect from a **server-only Node.js** adapter using `pg` (already a dependency) and a secret connection string authenticating as that custom Postgres login. Supabase JS with a publishable key does **not** become this Postgres role merely because the SQL role exists. Supabase's supported choices are a direct Postgres connection for a persistent IPv6-capable backend, a session pooler for a persistent IPv4-only backend, or a transaction pooler for short-lived/serverless connections. Choose after confirming deployment topology; transaction mode requires avoiding session-state assumptions and named prepared statements. Copy the custom-role connection parameters from the approved project's Connect dialog; do not derive a pooler host or use the `postgres` owner login. Use TLS, bounded pool size, query timeout, connection rotation and server-only secrets. With a single direct read role, no `SET ROLE` is needed. The Admin session and directory are checked **before** opening/querying this pool; the DB role supplies least privilege, not per-user authorization. Source: [Supabase connection methods](https://supabase.com/docs/guides/database/connecting-to-postgres).

Rotate the database login credential through the secret manager with a controlled overlap/restart plan; close old pools and revoke the old credential after verification. Audit effective `has_schema_privilege`, `has_table_privilege`, role memberships, `pg_policies`, function EXECUTE and `current_user` in a disposable target. Log read operation name, request ID, Admin ID and outcome without SQL parameters, connection strings or tokens. Production audit and logging settings remain **unverified**.

## PostgreSQL adapter query plan — design only

The real adapter should use parameterized `pg` queries. Map the four sort enum values to four hard-coded ORDER BY and cursor predicates; never interpolate a URL sort or field. Validate page size <= 50 and request `LIMIT $n + 1`. SQL expressions below are plans, not executed statements.

1. Base candidates from `catalog_private.products p`. `status = $status` only when selected. Primary category: `EXISTS (SELECT 1 FROM catalog_private.product_categories pc WHERE pc.product_id=p.id AND pc.is_primary AND pc.category_id=$category_id)`. Do not match secondary links or collections.
2. Search trimmed, lowercased text against `p.product_code` and `EXISTS` on `product_translations t` restricted to `locale IN ('en','zh')`, using parameterized `ILIKE $pattern ESCAPE '\\'`. Escape backslash, `%`, and `_` in the user term before surrounding it with `%`. English is case-insensitive; Chinese is literal substring matching. The offline adapter currently uses JavaScript `toLowerCase().includes`; Unicode/collation equivalence needs an isolated parity test. Search is not performed on private attributes, SKU or arbitrary columns.
3. Original sort order: `updated_desc` = `p.updated_at DESC, p.id ASC`; `updated_asc` = `p.updated_at ASC, p.id ASC`; `product_code_asc` = `p.product_code COLLATE "C" ASC, p.id ASC`; `product_code_desc` = `p.product_code COLLATE "C" DESC, p.id ASC`. These key columns are NOT NULL in the SQL schema, so NULL placement is inapplicable. Product code's SQL constraint only requires trimmed nonempty text; unlike the app's ASCII code validation, it does **not** restrict its alphabet. Align the code contract or test Unicode ordering before using the C collation in production.
4. Apply signed cursor values only after the Repository verifies signature, scope, sort, filter, direction and boundary. For Next, use strict lexicographic comparison in original order: updated/code DESC means value `<` boundary; ASC means value `>`; on equality UUID `>` because the tie-breaker is ASC. For Previous invert both key comparisons and ORDER BY directions (including UUID DESC), fetch at most pageSize+1, then reverse the returned page back to original order. Use the extra row only to determine availability. Do not use OFFSET or a client-provided SQL fragment. When data can change between requests, keyset paging avoids offset drift but does not give a multi-request snapshot; document concurrent-update behavior separately.
5. Only after candidate page IDs are bounded, hydrate required translations, category links and ancestors, variants and images using parameterized `product_id = ANY($ids::uuid[])` queries. Preserve numeric as decimal strings and safely check bigint before UI mapping. Return the existing `PrivateCatalogBundle` shape; do not alter B1 DTOs or Public views. Source errors become `SOURCE_UNAVAILABLE`, never `NOT_FOUND` or raw SQL output.
6. Category options: select distinct *primary* `category_id` with category display names, ordered by English name then UUID, `LIMIT 51`; set `hasMore` and return at most 50. This is an Admin-only query behind the same permission check. Product existence for EMPTY vs NO MATCH must use a bounded `SELECT 1 ... LIMIT 1`, not a full catalog scan.

Existing relevant indexes: `products_public_listing_idx(status, featured DESC, updated_at DESC, id)`, `products_type_status_idx(product_type, status, id)`, `product_categories_one_primary_uq(product_id) WHERE is_primary`, `product_categories_category_idx(category_id, product_id)`, and translation PK `(product_id, locale)`. The public listing index does not directly cover all-status Admin updated sorting. The unique product-code index helps prefix/equality operations but not arbitrary `%term%` substring search. No SQL query or index has been executed for this plan.

## Signing key deployment — design only

`ADMIN_CATALOG_CURSOR_SIGNING_KEY` is server-only and must contain 32 cryptographically random bytes encoded as canonical base64url (43 characters). Development: use a local ignored environment file or secret manager value generated per developer, never an example default. Tests: generate a fresh random key at runtime inside the isolated child process. Preproduction/production: provision independent values through the platform secret manager; never use `NEXT_PUBLIC_`, source control, URL, rendered DTO or logs. All instances serving the same environment need the same current key. A new key invalidates outstanding cursors; a user should reset to page one after the safe invalid-query response. Coordinate rotation with instance rollout to avoid mixed-key failures; this design intentionally has no old-key fallback. Do not log raw cursors, signatures, cookies or DB parameters. No production key has been generated or installed by B2-C.

## Static performance and index assessment — design only

| Products | Static expectation | Index decision |
|---:|---|---|
| 100 | Bounded scans likely acceptable; test correctness first. | No new index now. |
| 1,000 | Sorts and substring search may become noticeable depending on distribution. | Measure representative query plans in an approved isolated database. |
| 10,000 | All-status updated sorts, primary-category filters and `%term%` name search may need targeted indexes. | Consider `(updated_at DESC, id ASC)` plus opposite mixed-direction variant if both directions are hot; a partial `(category_id, product_id) WHERE is_primary`; and `pg_trgm` GIN expression indexes on code/translation names if substring search is slow. Review write overhead and extension approval first. |

The product-code unique index already supports its uniqueness and ordered scans, though the explicit `COLLATE "C"` choice must be matched to index collation before claiming index-only sort performance. Reverse keyset queries need a compatible directional index or may sort bounded candidates. These are static inferences, **not** EXPLAIN ANALYZE results. Do not add indexes before query data, latency targets and production-like plans are measured.
