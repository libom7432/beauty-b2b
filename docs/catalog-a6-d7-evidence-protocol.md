# Sprint 2.7-A6-D7-P3 — 方案 B 来源与导出协议（审批草案）

**状态：DRAFT / NOT APPROVED / NOT EXECUTED。** 本文规定未来一次性 Supabase SQL Editor 人工元数据快照应留下的可复核证据，未证明 SQL Editor 当前具备所述记录或导出能力，也不授权访问目标项目。阶段状态继续为 `EVIDENCE_COLLECTED / PROVENANCE_PENDING / BASELINE_NOT_APPROVED / A6_BLOCKED`。当前 D1 的 `SOURCE_AUTHENTICATION_UNVERIFIED`、`RAW_EXPORT_COMPLETENESS_UNVERIFIED`、`NOT_INTEGRATED` 与正式 Overall `BLOCKED` 均不因本文改变。

本协议依据[方案 B ADR](catalog-a6-controlled-snapshot-adr.md)、[原连接契约](admin-catalog-supabase-snapshot-f2.md)、[A5 来源登记](catalog-a5-evidence-provenance.md)、[D7 准入清单](catalog-a6-d7-execution-readiness-checklist.md)及[旧规则集成设计](catalog-a6-d7-legacy-integration-plan.md)。A5 的十份历史 CSV 与本次 A6 快照是不同证据链；不重复历史权限审计，也不把历史哈希当作本次会话证明。

## 1. 证据分层与不可替代关系

**信任边界：** Project Ref 不能由数据库自报替代；SQL Editor 身份不能由文件名或包内相同哈希替代；原始导出完整性不能由转换后的 JSONL 自证。所有现场材料必须从独立于证据包的受控来源获取并有可复核的来源、原件哈希及签署。若平台无法提供足以证明完整执行 SQL 或导出覆盖的材料，维持 `UNVERIFIED` 并停止正式验收，另行申请可审计的执行／导出方式。

## 3. 取证时：一条查询对应一个不可复用的执行 ID

1. 操作员在批准窗口内打开经批准项目，独立复核者从受信清单和现场 Dashboard 上下文核对 Project Ref、环境及账号。执行另行批准的数据库／完整版本／`current_user`／`session_user` 身份检查查询；保留实际执行语句、结果、UTC 时间与会话关联。SQL 自报身份只证明该结果声称的数据库身份，不证明 Dashboard 项目 Ref 或全部后续查询沿用同一会话。
2. 对每条获批查询登记**查询 ID**（例如当前 B1 固定的 `snapshot`）和本次独有的**执行 ID**；两者不能互代。执行前对实际粘贴的完整 SQL 作字节核对；执行后取得平台保存的完整实际执行文本／哈希、查询版本、项目上下文、操作员、数据库身份、UTC 时间、成功／错误、返回列名和类型、平台行数及结果限制设置。仅凭批准文件、编辑框截图或手写执行记录不足以证明实际执行字节。
3. 每次只运行一条批准 SQL。成功后立即按批准方式导出原始结果，记录导出动作／来源 ID、UI 显示的总行数、列名、是否分页、导出上限及文件名。若 SQL Editor 不提供可信总行数或完整导出能力，不得把 `truncated:false` 当作事实；维持完整性 `UNVERIFIED` 并停止，后续分页或替代导出须另行审查精确 SQL 和契约。
4. 发生项目／身份／SQL 哈希不符、SQL 执行失败、超时、权限错误、导出不完整或字段异常、静默截断嫌疑、会话切换、意外对象／权限／RLS、日志缺失或越界操作时，立即停止后续查询。保留失败记录及已取得原件，标记失败或隔离；不得用重跑覆盖原执行 ID、原件或错误日志，也不得现场 GRANT／REVOKE、修改 SQL 或迁移。

每次执行记录的最小字段：查询 ID、执行 ID、批准记录 ID 与 SQL SHA-256、实际完整 SQL／其 SHA-256、Dashboard 项目 Ref 与环境的独立现场证据索引、具名操作员与账号、`current_user`、`session_user`、数据库名及完整版本、UTC 时间、成功／错误、列名及类型、平台显示行数、结果／导出上限、分页状态、导出动作 ID、原始文件名。记录每个字段的来源为“平台记录／外部现场证明／SQL 自报／人工转录”，不得混写成同一可信等级。

## 4. 取证后：原件、转换和独立复核

1. 将**未经编辑的原始 CSV** 先保存到批准的受限位置，立即计算完整文件字节 SHA-256，并记录文件大小、导出动作／执行 ID、采集 UTC 时间及保护措施。保留原始文件不变；如需修正导出，使用新的执行或导出 ID 和新文件，不覆盖旧件。限制访问并保留版本／审计日志；复核者在独立时点重算哈希。
2. 对当前 A1 `snapshot`，B1 只接受 UTF-8 CSV 的唯一标题 `snapshot_row`，每条数据为一个非空 JSON 对象单元格；允许规范 CSV 引号转义及引号内换行。确认 SQL Editor 实际原始导出恰好符合此结构。若它添加额外列、注释、BOM、结果限制说明或采用别的格式，**不要伪称转换后的文件为原始 CSV**；保留真原件并提交格式适配／验证器变更审批，在此之前 B1 不得当作已验证。
3. 按预先审查的确定性规则将每个原始 `snapshot_row` JSON 对象转换为一行 UTF-8 JSONL；保留原行顺序，不删除／补造／去重／改写字段或 NULL，不作业务数据清洗。记录转换工具版本、输入／输出 SHA-256、行数及操作员；B1 可比较 CSV 与 JSONL 解析后的对象是否逐项一致，但该比较不证明 SQL Editor 导出完整性。
4. 独立核对原 CSV、JSONL、平台显示总行数、列名／类型、导出上限与完整导出证明；检查重复 `row_key`、缺失或多余 section、`section_inventory` 动态计数、角色／成员／ACL 和 NULL 标记。零行须由平台证据和预期 section 合同支持，不能仅凭空文件宣称完整。任何 UI 行数与导出行数差异或无法证明上限，均标记 `RAW_EXPORT_COMPLETENESS_UNVERIFIED`。
5. 将批准 SQL 文件、执行记录、原始 CSV、转换 JSONL 与 Manifest 按查询 ID／执行 ID 一一绑定；逐文件登记原始 SHA-256，并由独立复核者从受控原件重算，确认没有多余／缺失文件。包内 Manifest、执行记录或 `rawExportSourceId` 可帮助一致性检查，**不能凭包内自报值认证来源**。签署的目标／身份／导出证明与受控原件索引留在证据包外，防止同一人同时改写文件和“独立锚”。
6. 采集者签完整性和操作事实，独立复核者签原件、现场来源、逐次执行及转换绑定，项目负责人签目标和授权范围，数据库安全负责人签高权限执行偏差及证据保护。签名记录均写明姓名或可核身份、角色、结论 `APPROVE / REJECT / PENDING`、适用查询／执行 ID、文件或记录哈希、证据索引、UTC 时间及限制条件。未签、缺证或结论 PENDING 时不得进入正式安全验收。

## 6. 与 B1/D1 当前输入契约的对齐和差异

| 事项 | 现有代码已支持 | 正式来源／导出仍缺的部分 |
| --- | --- | --- |
| 批准锚 | B1 接受证据包外 policy 文件及独立 SHA-256；D1 另要求包外 baseline、哈希和独立 `trustedTarget` | 签署者身份、批准记录、会话窗口、查询用途和实际平台目标须由外部信任渠道提供；验证器不得自行生成或把包内 Ref 升级为可信 Ref |
| 单次快照包 | B1 固定一条 `snapshot` 查询；policy、Manifest 和记录限定项目 Ref、数据库、版本、operator、`currentUser`、`sessionUser`、SQL 版本／哈希、文件路径／哈希、`rawExportSourceId`、行数、`columns:["snapshot_row"]`、`truncated:false` | 平台完整 SQL 原文／来源、Dashboard 账号权限、平台执行／导出 ID、行数和列类型、结果限制／分页设置、采集者与复核者签名均无外部认证字段；`success:true` 和 `truncated:false` 是待证事实，不能由记录自报确证 |
| CSV／JSONL | B1 核 UTF-8、CSV 单列标题、JSONL 行、原件与转换结果解析一致、行数／section 计数和哈希；D1 在调用 C1 前后重读并核固定文件哈希 | 原始 CSV 必须是真正 SQL Editor 导出且证明未截断；转换规则、工具版本、原件保管和独立复核签署目前在包外，须另立审查记录 |
| 失败闭锁 | B1 阻断不一致，D1 对 B1 失败或重读变化返回 BLOCKED，且正式 Overall 无 PASS 路径 | 不能据此把 `SOURCE_AUTHENTICATION_UNVERIFIED`、`RAW_EXPORT_COMPLETENESS_UNVERIFIED` 或 `legacyCheckerStatus:NOT_INTEGRATED` 视为已完成；独立来源认证阶段尚未实现 |
| 格式与扩展 | B1 只接纳单条 `snapshot`、固定四个子目录及 Manifest；A1 输出 JSON 对象列 `snapshot_row` | 现场 SQL Editor 导出格式若不同需先批准适配；另行的身份检查和 version-only 迁移历史查询不在当前 B1 单查询包内，需独立证据及后续契约／代码适配，不能塞入未声明文件或伪装成 `snapshot` |

外部签署记录的最小附加字段：受信项目清单版本／签署、Dashboard 账号和权限证明、实际完整 SQL 来源及独立哈希、平台查询与导出 ID、平台列名／类型和返回总行数、结果限制／分页设置、受控原件存储与访问日志、采集者／独立复核者身份及签名、审批范围和 UTC 时间。这些字段不能由 B1/D1 根据包内文件自动补全；未来若扩展代码，应保留独立来源与信任锚，不允许调用者用自填布尔值宣称 `AUTHENTICATED`。

## 7. 审批分工、停止条件与剩余闸口

| 角色 | 必须作出的独立决定或记录 |
| --- | --- |
| 项目负责人 | 确认受信目标、操作员、查询白名单、单次时间窗和取证范围；批准执行并签目标来源，不代签安全风险或独立复核 |
| 数据库安全负责人 | 审核 SQL 函数／元数据范围、SQL Editor 实际权限与强制只读偏差、受限存储和高权限剩余风险；未接受风险则否决执行 |
| 具名操作员／采集者 | 在获准窗口逐条操作，保存真实执行、失败与导出原件，记录每个查询和执行 ID；遇异常立即停止 |

**立即停止：** 无双签执行授权、目标或身份不符、SQL 字节／函数白名单变化、权限或会话范围不明、失败／超时／权限错误、原文或导出日志缺失、返回列或行数不符、结果可能截断、CSV 格式不兼容、文件被覆盖／替换、未知权限／对象／RLS 变化，或任何写入／授权／迁移企图。停止后保留已有审计记录并标注失败；不得自动重试、修复权限或把不完整结果送入正式安全验收。
