# Sprint 2.5-B4.5-A catalog transaction contract

This stage defines server-side types and an **offline, single-process Mock** in `src/lib/catalog-import/transaction.ts`. It has no SQL, database client, network call, API route, or production credential. B2's six `catalog_private` tables and B3/B4.4 contracts remain the source of truth. The Mock demonstrates state transitions and rollback; it is not a production transaction manager.

## Adapter and trust boundaries

`CatalogSnapshotReader.readRows()` must read complete rows from `products`, `product_variants`, `categories`, `product_categories`, `product_images`, and `product_translations`, including drafts, retired records, and all B2 columns. The future implementation must use a controlled server connection with `catalog_import` or `catalog_admin` rights, explicit column lists, and one consistent transaction snapshot. Anonymous `catalog_public` views are insufficient: they omit private and retired state and some columns. `mapCatalogDatabaseRows` converts PostgreSQL timestamps to ISO strings, safe `bigint` to numbers, numeric prices to decimal strings, and preserves `NULL` as `null`. It rejects missing columns and unsafe integers. `readCatalogSnapshot` passes all rows to B4.4-A `captureTrustedCatalogSnapshot`, which checks identities, relationships, publication integrity, freezes the graph, and computes SHA-256. Only this server-side reader may call the trusted constructor in production. Its TypeScript type or a client-supplied JSON object is not proof of trust.

The intended pipeline is **client file bytes → B4.2/B4.3 server parse → normalized batch → trusted database snapshot → B4.4-B final merge/B3 validation → B4.4-C diagnostic report → server-authenticated transactional request → database result**. Neither a client snapshot nor `report_id` authorizes a write. `verifyCatalogActorContext` accepts only the result of an injected server-side session verifier and brands that object in-process; `execute` rejects a copied/client-constructed object even if its role strings match. The Mock verifier is a test fixture, not an authentication system. B4.5-B must inject the real server session verifier from a fixed server module, never from request data. The server must never accept actor role, real product/SKU/image UUID, or final write rows from the browser. The normalized batch must be produced by the server parser, not deserialized from a client DTO. No public import endpoint exists at this stage.

`TransactionalImportRequest` carries `import_batch_id`, `idempotency_key`, `expected_snapshot_version`, `import_source`, server-produced `normalized_batch`, and verified `actor_context`. Excel requests must carry the **complete** B4.3 conversion result so formula and mapping errors cannot be discarded by passing only `parsed`; CSV requests carry the B4.2 result. `CatalogImportTransaction.execute` returns a `DatabaseWriteResult` with commit/no-change status, new snapshot version, product count, preview-to-database identity map, and replay flag. The identity map is internal server data, not a public API response. Existing UUIDs remain unchanged. New products, SKUs, and images get fresh database UUIDs. The Mock allocates deterministic UUID-shaped test values and calls `assertNoPreviewCatalogIds` on the resulting rows; B4.5-B must use PostgreSQL-generated UUIDs or a controlled server allocator. `preview:product`, `preview:variant`, and `preview:image` values never enter UUID columns.

## Transaction lifecycle and ordering

1. Authenticate actor and authorize import/admin role outside SQL. Validate request envelope, parser result, and idempotency key.
2. Begin one database transaction on one connection. Acquire locks in canonical order, with bounded lock and statement timeouts. Check a durable idempotency record by `(actor_id, idempotency_key)` under its unique constraint. Same request fingerprint returns the stored result; a different fingerprint returns `IDEMPOTENCY_CONFLICT`.
3. Read all six private tables through the controlled reader under the protected transaction. Recalculate the B4.4-A digest. Compare the expected version: mismatch yields `SNAPSHOT_STALE` and rollback.
4. Re-run B4.4-A identity resolution, B4.4-B complete Patch merge, and B3 final-state validation against the locked snapshot. Any error yields `BATCH_INVALID` and rollback. A no-change batch records its idempotent result but performs no catalog DML.
5. Allocate real UUIDs and maintain a private preview-to-real map. Apply rows in FK order: products; product_variants; product_translations; product_categories after verifying existing categories; product_images after SKU IDs resolve; final product status and `published_at` transition. Existing rows use UPDATE; absent rows use INSERT. The current import contract does not delete omitted rows or physically delete product/SKU/category identities.
6. Let PostgreSQL unique indexes, foreign keys, row guards, RLS, and deferred publication triggers check the final state at commit. Commit catalog changes and the idempotency receipt atomically. Return the stored result. Never return a success receipt before commit.

B2's deferred constraint triggers allow child rows to be assembled in one transaction and verify published products at its end. The SQL unique constraints on product code, slug, SKU, normalized SKU attribute combination, primary category, and image storage key remain the final arbiters. No application check can weaken them. Published products require a published SKU, active primary category, complete English/Chinese translations, and a published primary image with two ALT texts; retired products cannot retain a published SKU. B2 does not contain an idempotency table. B4.5-B needs a separately reviewed migration before a production write path can exist.

## Concurrency and idempotency

The Mock serializes every import with one in-process gate. This makes its tests deterministic but provides no cross-process safety. For initial PostgreSQL implementation, choose **READ COMMITTED**, a transaction-scoped advisory lock with one fixed application namespace/key, then take `SHARE ROW EXCLUSIVE` locks on all six private catalog tables in fixed order **categories → products → product_variants → product_categories → product_images → product_translations** before reading any snapshot rows. This blocks ordinary writes that bypass the advisory protocol while the import is active and ensures the six reads occur after preceding writers commit. Then lock affected category and product rows in sorted UUID order; use the same order for SKU and child rows. A fixed global lock limits concurrency intentionally at 100–10,000 products; later fine-grained locks require a separate correctness review. All catalog write paths, including manual product editing and category-tree administration, **must** use the same advisory key and lock order. A path that bypasses it may block on table locks during an import, but can otherwise race with other bypassing writers and invalidate their own previews. Restrict direct table writes to controlled services and audit all role grants. Do not claim that advisory locks protect against a noncooperating writer.

Maintain bounded `lock_timeout` and `statement_timeout`; map SQLSTATE `40P01` (deadlock), `40001` (serialization failure if isolation is later tightened), `55P03` (lock unavailable), and timeout to retryable conflicts after full rollback. Uniqueness violations (`23505`) are conflicts, never partial success. The table-lock choice must be tested locally for compatibility with B2's `catalog_import` grants and deferred publication triggers. It is intentionally broader than row locks; if it proves too costly, B4.5-B must replace it with a separately reviewed multi-writer protocol rather than silently omitting it. All catalog table names remain schema-qualified. RFQ tables are outside this lock scope.

This handles two admins changing one SKU, adding the same SKU, changing one translation, or changing category state while an import is pending: only one import validates and commits at a time. The second rereads the complete state, sees a stale digest, and must get a new preview. Two identical concurrent requests with one idempotency key serialize on a unique `(actor_id, idempotency_key)` record; the later request returns the first committed result. The fingerprint is SHA-256 over the batch ID, canonical server-normalized rows, CSV/Excel conversion issues, import source, and expected version. Same key with different fingerprint is a conflict even if the resulting business state might match. Failed transactions leave no success receipt, so a retry can run from a fresh snapshot. If the client times out or the response is lost after an ambiguous commit, retry with the **same** actor, key, batch ID, and request bytes; the committed receipt resolves whether it succeeded. Never switch keys to guess. A durable record needs a fingerprint, committed result, creation and commit times; enforce uniqueness in PostgreSQL, not only in the browser.

## Atomicity, errors, and RFQ boundary

The Mock builds a detached working copy, checks it with `captureTrustedCatalogSnapshot`, then swaps it into memory once. Injected failures after product, SKU, translation, category link, image, precommit work, **or receipt creation** leave both catalog state and idempotency map unchanged. In PostgreSQL, any insert failure, uniqueness/foreign-key conflict, publication failure, authorization failure, stale version, deadlock, connection loss, or timeout must roll back **all** products in the batch and the idempotency receipt. Do not retry an ambiguous commit with a new key; query the durable receipt with the same key and fingerprint first.

Stable application errors: `PERMISSION_DENIED`, `INVALID_REQUEST`, `IDEMPOTENCY_CONFLICT`, `SNAPSHOT_STALE`, `BATCH_INVALID`, `TRANSACTION_TIMEOUT`, `WRITE_FAILED`. Later SQL adapter maps database errors to these or more specific public codes while withholding SQL text, connection details, and private values.

The B2 `catalog_import` role has private table SELECT/INSERT/UPDATE and no DELETE. Anonymous users only read vetted `catalog_public` views. `rfq_api` has no new catalog grants and remains separate; its RFQ privileges, LOGIN state, and submission switch are unchanged. The future import service needs separate connection provisioning and permission acceptance before it can execute SQL.

## B4.5-B implementation plan

1. Use a **disposable local PostgreSQL database or container** with a dedicated test database name and role. Before connecting, guard the target host, port, and database name against a local allowlist and reject any production/Supabase URI. Initialize only approved local copies of B2 prerequisites and catalog migration, plus a separately reviewed B4.5-B idempotency migration. Record `pg_current_wal_lsn()`/schema inventory before and after tests; drop the disposable database or container on completion. Never run migrations against an unverified target.
2. The later D1 draft supersedes the original receipt sketch: `catalog_private.catalog_import_receipts` uses `(actor_id,idempotency_key)` as its primary key, a 64-hex `request_fingerprint`, allowlisted `result jsonb`, `created_at`, `completed_at`, `retry_until` (30 days), `result_purge_after` (90 days), `expired_at`, and a permanent `expired` tombstone. Insert the **committed** receipt in the same transaction as catalog DML; a rollback removes both. Same-key replay is allowed only through `retry_until`; an expired key is never reused. No durable `in_progress` claim is required for the initial design. The D1 SQL is a review draft and has not been executed.
3. Audit B2's existing `catalog_import`/`catalog_admin` privileges, RLS and `catalog_private` exposure. The future SQL adapter needs explicit-column SELECT on the six private tables, INSERT/UPDATE on the importable product tables, and narrow receipt INSERT/SELECT. It must not use `rfq_api`, `anon`, browser credentials, or a bypass-RLS service credential. B2 currently grants `catalog_import` UPDATE on categories even though this import contract does not change category definitions; B4.5-B must review that breadth and ensure the adapter issues no category DML. Do not change those permissions in this stage.
4. Use one acquired connection per transaction: `BEGIN ISOLATION LEVEL READ COMMITTED`, set local timeouts, acquire the fixed advisory lock, acquire six table locks in the documented order, reread the complete snapshot, check version, resolve/merge/B3-validate, allocate UUIDs, write in FK order, insert the receipt, and `COMMIT`. Verify all SQL uses schema-qualified identifiers and parameters. Local concurrent-connection tests must cover lock waits, unique conflicts, trigger checks at commit, rollback and response-loss replay. The Mock is single-process and cannot prove those properties.
5. Keep the production import route **absent or explicitly disabled by default**; any future route requires separate authentication, authorization, rate/size limits, audit logging, and rollout approval. For RFQ noninterference, compare RFQ schema objects, role grants, RLS policies, and the RFQ submission switch before/after local tests; run existing RFQ regression and assert the catalog migration does not grant catalog access to `rfq_api`. No RFQ customer data is needed.
