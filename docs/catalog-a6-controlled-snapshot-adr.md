# Sprint 2.7 A6-D2 — Controlled SQL Editor Snapshot Contract Amendment (ADR draft)

**Status:** PROPOSED; project owner and independent security review pending. A6-D0 approved Scheme B as a **design direction only**. This draft does not authorize SQL Editor execution, database changes, a migration, or a security baseline PASS.

**Target:** `beauty-b2b-catalog-dev`, Project Ref `nnmdcezigmguqolbxzmb`, database `postgres`, expected PostgreSQL 17.11. These are target identifiers from project handoff, not a fresh connection verification. The execution operator must verify them against trusted project inventory and the live SQL Editor context before each approved session. The earlier statement in `docs/catalog-only-dev-isolation-f1.md` that this project had not yet been created is historical; it cannot establish the project's present identity or existence.

**Existing contract:** [`docs/admin-catalog-supabase-snapshot-f2.md`](admin-catalog-supabase-snapshot-f2.md). This ADR proposes an amendment; the existing contract, snapshot SQL, and checker remain unchanged until separately approved and implemented.

## 1. Decision proposed and scope

For the current one-time A6 metadata snapshot, use a human-operated, controlled Supabase SQL Editor session with an explicitly approved execution identity and exact, independently reviewed read-only query versions. Do not create `catalog_audit_meta` solely to run this snapshot. A later recurring audit may require a different execution architecture and a separate decision.

Scheme B changes **how snapshot queries are executed**. It does not change the application runtime role `catalog_admin_reader_runtime`, its migration contract, RLS, effective privileges, or any database grant. An SQL Editor operator may have broad database privileges. A SELECT-only allowlist and human procedure are operational controls; they are not a database-enforced least-privilege or read-only role. The actual `current_user`, `session_user`, dashboard account/operator, and effective permission boundary must be recorded rather than assumed from the SQL Editor label. A read-only dashboard feature, if used, requires the same identity and effective-privilege verification.

## 3. Controlled SQL Editor execution protocol (proposed)

**Before:** The project owner selects and signs the exact project Ref, environment, database, operator, SQL Editor access route, intended DB execution identity, permitted query identifiers, full executable SQL text and SHA-256 values. A separate reviewer checks each statement's referenced objects and exact function calls, with no dynamic SQL, DDL, DML, role/ACL/RLS change, migration-body read, or business-table read. Keep an immutable versioned SQL file and hash the exact UTF-8 bytes that the operator will paste/run; define query start/end including comments, whitespace, terminator and line endings in the approval record. An edited paste is a new version and must be reviewed again. Verify the project name/Ref from a trusted project inventory and visible SQL Editor project context independently of database self-report, and execute a separately approved identity check for database, `server_version`, `current_user`, `session_user`, and UTC time. A prior A5 screenshot does not bind this new session or every query.

**During:** Execute one approved query at a time. Preserve the SQL Editor's **actual complete executed statement** (query-history record, full statement export or equivalent verifiable record), not just the approved source file or a partial screenshot. Capture query ID, executed SQL bytes/version, SQL hash, target Ref, DB identity, UTC start/end or recorded execution time, success/error, row count, column names/types, and the SQL Editor result-limit setting or equivalent completeness evidence. Keep a unique per-execution identifier through export. If the editor truncates output, stop; use only separately reviewed pagination/export SQL. Do not silently modify a failed query, grant permissions, repair data, or continue after an identity or version mismatch. If a read-only transaction is claimed, preserve evidence that all relevant statements ran in that same read-only transaction; otherwise record that database-enforced read-only was unavailable.

**After:** Export every complete raw result to restricted storage outside Git. For **each** execution, bind approved file path/version/hash → independently verified Project Ref → actual full executed SQL/hash → `current_user`/`session_user` and operator → UTC execution time and success record → unique execution ID → original result filename/hash, row count and column schema. Record the collector and independent reviewer who checks each link. If JSONL conversion is needed for the existing checker, preserve the untouched export, document the conversion and hash both files. The reviewer checks filename-to-query mapping, headers, missing/duplicate rows and keys, expected coverage, NULL/absent roles and schemas, unexpected rights, and export truncation. Empty results are recorded explicitly and are not an automatic security PASS. Store screenshots, logs, full CSV/JSONL and signed records in an access-controlled evidence location; the repository contains only non-sensitive references and hashes.

**Approved-function review boundary:** The current `scripts/catalog-supabase-permission-snapshot.sql` uses metadata introspection and permission checks from `pg_catalog`: `acldefault`, `aclexplode`, `has_database_privilege`, `has_function_privilege`, `has_schema_privilege`, `has_table_privilege`, `pg_encoding_to_char`, `pg_get_expr`, `pg_get_function_identity_arguments`, `pg_get_userbyid`, `pg_get_viewdef`, `oidvectortypes`, and `to_regclass`. It also uses built-in value/format/aggregation helpers `current_database`, `current_setting('server_version')`, `format`, `count`, `coalesce`, `jsonb_agg`, `jsonb_build_object`, `md5`, `strpos`, `to_jsonb`, and `unnest` (with `pg_catalog.` qualification in the SQL where shown). This is a **candidate allowlist for this exact query version**, not blanket approval: independently confirm every function's resolved `pg_catalog` identity, argument values, PostgreSQL 17.11 behavior, and lack of database/session side effects before approving execution. The separately reviewed `scripts/catalog-supabase-migration-history.sql` reads only `version` from `supabase_migrations.schema_migrations` when that table exists and access is authorized. PostgreSQL 17 documents the privilege-inspection and definition functions as system information functions; function volatility alone is not a complete safety proof. `SELECT` and the `pg_catalog` schema can also expose effectful calls such as `set_config` or `pg_terminate_backend`; these and any user-defined, extension, `SECURITY DEFINER`, dynamic-execution or unlisted function are prohibited absent a new independent review. See the PostgreSQL 17 System Information Functions, System Administration Functions, and Function Volatility documentation linked below.

**Evidence failure rule:** If the actual complete executed SQL cannot be compared with the approved bytes, or the execution record cannot be reliably linked to its original result export, record `Provenance = PENDING`; **Evidence Validation must not PASS**, and **Security Baseline Validation must not be approved from that result**. Re-running or guessing a hash does not repair the missing historical link.

**Residual risk:** A privileged SQL Editor session can execute statements beyond the approved SELECT list unless a separate database mechanism enforces restrictions. Operator review, limited session duration, access control, query allowlist and two-person sign-off reduce misuse risk but cannot prove that the DB role was read-only. The project owner and DB/security owner must explicitly accept this deviation before an actual snapshot run.

## 4. Validation outcomes remain separate

**Evidence Validation** tests project and session identity, approved SQL bytes/hash against the actual executed SQL, per-query execution-to-export binding, complete untruncated result, raw-file hash, schema/row coverage, and collector/reviewer binding. It can pass only for an actually collected and reviewable snapshot; the evidence failure rule above applies even when row counts and hashes of the local files match.

**Security Baseline Validation** compares the actual snapshot against a separately signed, exact allowlist of role attributes, membership edges including grantor and all three options, object/ACL source, PUBLIC/effective permissions, RLS, functions and migration stage. Unknown roles, expanded permissions, missing/duplicate rows and unexplained high-privilege paths block. Evidence Validation may pass while Security Baseline Validation remains blocked. No role-name prefix or historical count is an approval rule; A5's observed 30 roles/24 edges are a completeness reference, not an eternal platform invariant.

The current A5 statuses remain `PROVENANCE_PENDING` and `BASELINE_NOT_APPROVED` (with `EVIDENCE_COLLECTED` and `A6_BLOCKED`). Existing ten CSV byte/structure checks do not prove per-query execution identity, time or Ref, and do not sign the permission baseline. Neither this ADR nor its hash upgrades those states.

## 5. catalog_admin_reader_runtime TEMP Privilege Conflict

The A5 evidence records current database `PUBLIC` CONNECT and TEMPORARY, and `public` Schema `PUBLIC` USAGE. PostgreSQL 17 grants `PUBLIC` privileges to every role; database TEMPORARY permits creation of temporary tables. The existing Catalog-only checker requires `catalog_admin_reader_runtime` effective database TEMP=false at `admin-read` and treats PUBLIC database TEMP as a blocker. **The Admin Read migration itself** (`supabase/migrations/20261020120000_add_catalog_admin_read_runtime.sql`) calls `has_database_privilege(..., 'TEMP')` and raises an exception when it is true. Revoking that role's direct TEMP grant cannot cancel an effective TEMP grant from `PUBLIC`. `NOINHERIT` would not cancel `PUBLIC` either. The runtime role's actual future effective TEMP remains unverified until a post-migration snapshot exists; if PUBLIC TEMP remains unchanged, the migration's own assertion would fail. Changing only the snapshot checker cannot make that migration pass.

This is an **application runtime privilege conflict**, independent of the SQL Editor audit execution identity and of whether `catalog_audit_meta` is created. TEMP is distinct from database CREATE, Schema CREATE and business-table DML, but it permits database-side temporary-object activity and associated resource/session risk. The current runtime role therefore cannot be declared least-privilege compliant under the old TEMP=false contract.

| Later resolution direction | Security property | Supabase/platform impact | Cost and approval |
| --- | --- | --- | --- |
| Database-level permission adjustment: plan a PUBLIC TEMP revoke, with explicit narrowly scoped TEMP grants only to roles proven to need it after platform dependency analysis | Can enforce runtime TEMP=false at the database ACL layer if no other path grants it; must re-test effective permissions and operations | Potentially affects Supabase-managed services and other roles on the same database; platform/security owner must confirm compatibility | Medium to high review and rollout cost; separate database permission-change/security approval, rollback and platform validation required. **No change authorized now.** |
| Isolated environment: place Catalog runtime in a separately controlled database/project whose PUBLIC/default ACL can satisfy TEMP=false; define approved data flow and connection boundaries | Stronger privilege separation without changing the existing project's PUBLIC TEMP, subject to verifying the new environment's ACL and role paths | Requires new Supabase resources or architecture, connection and data-flow changes | High design/operational cost; separate architecture, data, budget and security approval required. **No change authorized now.** |
| Independently approved contract revision: if TEMP=true must be tolerated, request an explicit revision of the runtime minimum-privilege contract and corresponding migration/checker assertions, with documented compensating controls | Operationally mitigates risk but **does not** satisfy the existing TEMP=false assertion or make TEMP database-forbidden | Avoids immediate platform ACL changes | Lower implementation cost, ongoing residual risk; requires a new owner/security risk decision and later code review, not a silent exception |

Do not remove the checker or migration assertion, ignore TEMP, or alter platform grants as part of Scheme B. No direction above has been selected or approved. **Do not authorize the Admin Read migration while this conflict remains unresolved.** Until a separately approved resolution is implemented and verified, Security Baseline Validation remains blocked for the affected runtime requirement.
