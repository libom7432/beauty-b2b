# Sprint 2.5-B4.5-D2-C1: receipt lifecycle maintenance

## Scope and current state

This stage adds an **offline contract**, synthetic tests, and an independent SQL **draft**. It does not connect to PostgreSQL, execute the draft, schedule a worker, change existing database permissions, or run a cleanup. The existing receipt table has `(actor_id,idempotency_key)` as a permanent primary key, a 64-character request fingerprint, `completed_at`, `retry_until`, `result_purge_after`, `expired_at`, `status`, and JSONB `result`. Its constraints require `retry_until = completed_at + interval '30 days'` and `result_purge_after = completed_at + interval '90 days'`. `committed` rows have a result; `expired` rows have no result and retain the key and fingerprint. An index covers due committed rows. RLS and FORCE RLS are enabled.

The executed local receipt access hardening removes direct receipt SELECT from `catalog_import` and `catalog_admin`; `restricted_v1` uses a single-key lookup function. The original maintenance role is named **`catalog_receipt_maintenance`**, not `catalog_import_maintenance`. It is NOLOGIN and non-bypass. The currently executed schema still grants it due-row metadata SELECT and narrow UPDATE of `status`, `result`, `expired_at`. This C1 draft would replace those direct grants with one fixed function. The actual production administrator identity provider, maintenance login, task scheduler, and production connection are **not implemented**.

## Lifecycle and time boundaries

| Period, using database time | Receipt behavior |
| --- | --- |
| From commit through `retry_until` inclusive | The same actor/key/fingerprint may replay the original allowlisted result. |
| Strictly after `retry_until` | Same request returns `IDEMPOTENCY_KEY_EXPIRED`; a different fingerprint returns `IDEMPOTENCY_CONFLICT`. No new import under the old key. |
| Through `result_purge_after` inclusive | Full allowlisted result remains stored for controlled recovery/audit, but the replay window has ended. |
| Strictly after `result_purge_after` | Approved maintenance may set `status='expired'`, `result=NULL`, `expired_at` to the captured database statement time. It never deletes the row. |
| Thereafter | Actor, key, fingerprint and lifecycle timestamps remain permanent; the composite primary key continues to prevent reuse. |

The import adapter obtains one `clock_timestamp()` for `completed_at` and derives both deadlines in PostgreSQL. Its restricted lookup computes replay eligibility with PostgreSQL `clock_timestamp() <= retry_until`. The stored `result_purge_after`, not a newly calculated deadline, is the 90-day authority. After acquiring the lock, the proposed purge function captures one database `v_cutoff := statement_timestamp()` and uses **strict** `result_purge_after < v_cutoff` for candidate selection and update, and `v_cutoff` for `expired_at`. The complete result remains at the exact 90-day boundary. Its RLS policies use `statement_timestamp()` for the same statement-wide database-time cutoff; they cannot make the function select a row whose deadline is not before `v_cutoff`. The existing direct maintenance RLS policy uses `<= now()`; the draft removes that policy and direct UPDATE. The offline clock is only a deterministic test fixture, never an authorization or production timing input. A privileged host clock change is an infrastructure risk outside this module.

## Least-privilege interface

`docs/sql/catalog-receipt-lifecycle-maintenance.draft.sql` is an incremental, transactional draft following the already executed receipt migrations. It does not edit or replay those migrations. It creates `catalog_receipt_lifecycle_owner` as NOLOGIN, NOINHERIT, non-superuser, without BYPASSRLS. That owner receives only due-row metadata SELECT and UPDATE of `status`, `result`, `expired_at`. It does **not** receive SELECT on `result`, DELETE, product-table rights, or RFQ rights. FORCE RLS remains enabled; two owner-specific policies permit only due committed rows to become expired tombstones. The owner is not a maintenance login.

The fixed `SECURITY DEFINER` function `catalog_private.purge_due_catalog_receipt_results(integer)` takes a batch limit of 1–500, tries the catalog transaction advisory lock without waiting, selects due keys in index order with row locks, updates only the three allowed columns, and returns **only an integer count**. A busy lock raises PostgreSQL standard SQLSTATE `55P03` (`lock_not_available`), which the service maps to `CATALOG_RECEIPT_MAINTENANCE_BUSY`; it never returns a misleading zero count and runs no UPDATE. It has no dynamic SQL, uses qualified objects, and pins `search_path` to `pg_catalog, pg_temp`. The draft revokes PUBLIC EXECUTE and the maintenance role's old direct table grants/policies; only `catalog_receipt_maintenance` receives EXECUTE. `catalog_import`, `catalog_admin`, `anon`, and PUBLIC receive no maintenance access. The migration operator's temporary function-ownership membership and schema CREATE grant are revoked before COMMIT.

The draft is not a claim of effective PostgreSQL permission proof. Before execution, an approved isolated test must verify function ownership, effective grants, RLS/FORCE RLS under independent non-superuser logins, default privileges, SET ROLE, temp-object shadowing, schema CREATE, and rollback. If the SQL cannot provide these boundaries, change the draft and re-review before any migration. A dedicated maintenance LOGIN must be provisioned separately with membership **only** in `catalog_receipt_maintenance`; it must not inherit or assume import/admin/owner/RFQ roles. Ordinary admins and public clients must have no task trigger or credential.

## Execution contract and lock order

`ReceiptLifecycleMaintenance.runBatch(limit)` is a server-side orchestration contract, not a database adapter or public API. Its injected adapter must authenticate a trusted scheduled task by server-held credentials; authorization defaults to deny and cannot come from request JSON or headers. It starts one bounded transaction, tries the existing catalog advisory lock `725604510131`, invokes only the fixed purge interface and commits. A real adapter must use one verified, non-superuser PostgreSQL connection, `READ COMMITTED`, `SET LOCAL ROLE catalog_receipt_maintenance`, and bounded `lock_timeout`, `statement_timeout`, idle and overall transaction timeouts. It must verify the actual database target before SQL. The SQL function tries the same transaction-level lock so a direct authorized call cannot skip it; if the same transaction already holds it, the try succeeds. A lock-busy error is reported separately from an empty due batch and is safe to retry after rollback.

Import transactions take the advisory lock first, then lock the six catalog tables in fixed order, then access receipts. Maintenance tries the **same advisory lock first**, then locks only due receipt rows ordered by `(result_purge_after, actor_id, idempotency_key)`. It never locks catalog tables. Concurrent maintenance workers: one proceeds; contenders receive the busy error for later retry. `SKIP LOCKED` is an additional row-level safeguard. Each batch has at most 500 rows and one commit, avoiding a table-wide or long-lived maintenance transaction. A schedule repeats batches until a count below the limit, with a bounded number of batches per invocation to avoid unbounded runtime. At the exact 90-day boundary, the strict predicate skips the row; a later run can process it.

No still-replayable row can be due for purge: its 30-day deadline precedes its 90-day purge deadline. `COMMIT_UNKNOWN` import recovery still finds the original receipt within 30 days. A committed request whose response is lost after 30 days cannot replay, regardless of whether its full result remains for 90 days; an operational investigation must not create a new import under the old key. The existing `restricted_v1` lookup and advisory lock order remain unchanged. This draft does not address the known shared-role cross-actor receipt access risk.

## Failure recovery, retention and observability

The executor treats an exception before COMMIT as a failed batch, attempts ROLLBACK, and discards a connection whose rollback fails. After a COMMIT attempt, a lost acknowledgement is `COMMIT_UNKNOWN`; it must **not** claim that no rows changed or blindly replay side effects. A later scheduled run is safe because expired rows no longer satisfy `status='committed'`; PostgreSQL would have committed the whole batch or none. Each committed batch returns only `purged_count`. No receipt JSON, actor ID, key, fingerprint, SQL parameter, credential, or stack trace belongs in logs. Log task correlation ID, count, duration, stable outcome code and coarse database target label only; protect audit logs separately. Do not record result bodies in an external job queue.

The full result is retained for at least 90 days until a successful due batch clears it. Scheduling or outages can extend retention; an operational alert must report overdue counts without exposing receipt rows. Tombstone rows and fingerprints are retained indefinitely under the approved anti-replay policy, with capacity/privacy review before production. The worker must never `DELETE` or `TRUNCATE` receipts, never update actor/key/fingerprint/timestamps, and never touch catalog or RFQ tables. Rollback of a populated migration must disable execution and preserve the table and tombstones; dropping it would allow key reuse.

## Offline verification and PostgreSQL plan

`scripts/test-catalog-receipt-maintenance.mjs` uses an in-memory synthetic store and injected clock. It covers unauthorized requests, limits, 30-day inclusive replay, 90-day exact boundary, permanent fields, repeat runs, concurrent workers, interrupted batches, uncertain COMMIT and failed rollback. These tests verify orchestration behavior only; they do not prove the draft SQL's syntax, grants, RLS, query plan or actual PostgreSQL clock behavior.

The original receipt migration already defines `catalog_import_receipts_purge_due_idx` on `(result_purge_after, actor_id, idempotency_key)` **where `status='committed'`**. This excludes permanent expired tombstones and matches the batch order. The single `v_cutoff` gives the query a consistent range value, but index selection, RLS interaction and large-table behavior require `EXPLAIN (ANALYZE, BUFFERS)` on synthetic data after separately approved isolated migration. Keep table statistics current with normal `ANALYZE`/autovacuum; C2-A1 does not add or alter an index.

Before any later, separately authorized PostgreSQL test: lock the exact local physical target by host, port, database, login, data directory, listener, system identifier and server version; inspect baseline rows and privileges; review the final draft and run it with `ON_ERROR_STOP` inside its transaction. Use independent non-superuser maintenance, import, admin, anon and unrelated login sessions. Verify direct SELECT/UPDATE/DELETE denial for the maintenance caller, no `result` SELECT for the function owner, function-only EXECUTE, RLS/FORCE RLS, fixed result count, exact 30/90-day boundaries using synthetic database timestamps, two-worker contention, import/maintenance lock ordering, failure rollback, uncertain commit recovery, permanent uniqueness and clean teardown. Never change the host clock, run the actual 90-day production job, or test against production. RFQ permissions require a separate target audit if RFQ tables are absent in the isolated catalog database.

Production prerequisites remain: approved administrator authentication and dedicated maintenance task identity, a reviewed non-superuser runtime connection, strict target and permission tests, deployment/scheduling/alerting, retention approval, and resolution or explicit acceptance of the shared `catalog_import` cross-actor risk. The production import API stays closed.
